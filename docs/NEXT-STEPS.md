# Як жити далі

Що зробити після воркшопу, щоб це перестало бути демо й почало приносити
користь. По порядку — від найдешевшого до найдорожчого.

---

## 1. Підключити до своєї бази

Найменша зміна в усьому списку: правиш `.env`, код не чіпаєш.

**Крок перший — read-only роль.** Не підключай сервер під своїм робочим
користувачем, навіть «на пробу». Один раз виконай у своїй базі:

```sql
CREATE ROLE analyst_ro WITH LOGIN PASSWORD 'обов-язково-свій-пароль';
GRANT CONNECT ON DATABASE твоя_база TO analyst_ro;
GRANT USAGE ON SCHEMA public TO analyst_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO analyst_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO analyst_ro;
ALTER ROLE analyst_ro SET statement_timeout = '15s';
```

**Одразу подумай, чого ця роль бачити не має.** Персональні дані, паролі,
платіжна інформація — видавай `GRANT SELECT` на конкретні таблиці або зроби
окрему схему з представленнями, де чутливі колонки вже вирізані. `GRANT` на
все — найпростіший шлях і найгірший.

**Крок другий — журнал.** Скопіюй таблицю `audit_log` з
[db/init/01_schema.sql](../db/init/01_schema.sql) і дай ролі `INSERT` тільки
на неї. `UPDATE` і `DELETE` не давай: журнал, який агент може підчистити, не
є журналом.

**Крок третій — `.env`.** Постав свій DSN у `DATABASE_URL` і перезапусти
Claude Desktop. Усе.

**Не Postgres?** Міняється один файл — [server/db.py](../server/db.py). Там
уся робота з драйвером. Для MySQL це `mysql-connector-python` або
`PyMySQL` замість `psycopg`, для BigQuery — `google-cloud-bigquery`. Guard,
інструменти й решта коду не змінюються взагалі.

## 2. Описати свої дані коментарями

Це найдешевша дія з найбільшим ефектом, і саме її пропускають.

Модель не знає, що у вас `status = 4` означає «оплачено», а таблиця
`users_new_2` — актуальна, на відміну від `users`. Поки це знання живе тільки
в голові аналітика, агент гадатиме.

```sql
COMMENT ON TABLE orders IS 'Замовлення. Актуальна таблиця; orders_old не використовувати.';
COMMENT ON COLUMN orders.status IS
    'ПАСТКА: 4 = оплачено, 5 = повернення. Для виручки бери лише 4.';
```

**Що описувати в першу чергу:**

- колонки-статуси, де не всі значення означають те, що здається
- прапорці, які треба виключати (тестові акаунти, внутрішні користувачі,
  видалені записи)
- що означає `NULL` у конкретній колонці — «немає даних» чи «досі триває»
- одиниці виміру: копійки чи гривні, UTC чи місцевий час
- таблиці-двійники, з яких актуальна лише одна

**Антипатерни.** Не пиши `COMMENT ON COLUMN users.email IS 'Email'` — це шум,
який займає контекст і нічого не додає. Не описуй те, що видно з типу колонки.
Описуй те, що знає тільки людина.

Цикл зворотного зв'язку тут найшвидший у проєкті: правиш коментар — і одразу
бачиш іншу відповідь, без перезапуску сервера.

## 3. Дописати свої інструменти

Загальне правило, заради якого варто було приходити на воркшоп:

> Інструмент потрібен тоді й лише тоді, коли модель не може зробити це сама.

**Варто зробити тулом:** доступ до ваших систем (тікет-трекер, CRM, платіжний
провайдер), розрахунки за вашими бібліотеками, ML-моделі, дії з побічним
ефектом (створити задачу, надіслати звіт).

**Не варто:** побудова графіків, форматування таблиць, написання SQL,
підсумовування тексту, «розумний пошук» по результату запиту. Усе це модель
робить краще, а ваш тул лише звузить їй руки.

Мінімальний новий інструмент — це функція з докстрінгом, дописана в
[server/tools/](../server/tools/) і додана в список у
[server/main.py](../server/main.py). Пам'ятай: **докстрінг і є промпт**. Опиши
в ньому не тільки що робить функція, а й коли її викликати і чого не робити.

## 4. Задеплоїти для команди

Поки сервер живе на твоєму ноутбуці, ним користуєшся тільки ти.

Покроково — у [railway.toml](../railway.toml). Коротко: Railway,
база в тому самому проєкті, змінні оточення, `Generate Domain`. Колега додає
URL як конектор у Claude і нічого не ставить.

**Перед тим як вішати на реальні дані — прочитай
[deploy/AUTH.md](../deploy/AUTH.md).** Read-only роль захищає дані від псування,
але не від чужих очей. Публічний URL без авторизації над справжньою базою —
це не «потім допиляємо», це витік.

Якщо ви в Google Cloud — дивись у бік Cloud Run: там вхід через корпоративний
акаунт налаштовується на рівні платформи.

## 5. Куди рости далі

- **Більше джерел.** Той самий сервер може ходити не тільки в базу:
  документація з приватних репозиторіїв, тікети, дашборди. Цінність росте
  нелінійно, коли агент бачить і дані, і контекст навколо них.
- **Дії, а не тільки читання.** Завести задачу за результатом дослідження,
  надіслати звіт у робочий чат. Правило одне: дія з побічним ефектом
  підтверджується людиною, а не виконується мовчки.
- **Свої ML-моделі як інструменти.** `predict_churn` — шаблон. Той самий
  каркас працює для прогнозу попиту, скорингу лідів, детекції аномалій.
- **Семантичний шар.** Коли метрик стає багато, коментарів у схемі перестає
  вистачати: потрібне окреме місце, де записано, як рахується кожна цифра.

---

## Чого не робити

**Не давай агенту права на запис** «щоб зручніше». Один раз дозволивши
`UPDATE`, ти більше ніколи не будеш упевнена, що сталося з даними о третій ночі.

**Не роби тул-обгортку над тим, що модель уже вміє.** Кожен зайвий інструмент
з'їдає контекст і збільшує шанс, що модель обере не той.

**Не деплой на реальні дані без авторизації**, навіть «на один день для
тесту». Такі тести переживають своїх авторів.

**Не пиши довгий системний промпт замість опису даних.** Знання про дані
місце в базі — у коментарях до колонок, поруч із самими даними. Там воно
не розсинхронізується і працює для всіх, хто підключиться.
