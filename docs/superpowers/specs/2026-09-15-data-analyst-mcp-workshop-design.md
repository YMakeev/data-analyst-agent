# Дизайн: воркшоп «From Data to AI Engineer» — MCP-агент-аналітик

**Дата:** 2026-09-15
**Формат:** 50 хвилин живої практики, 20:00
**Статус:** на погодженні

---

## 1. Мета

За 50 хвилин учасник власними руками будує MCP-сервер, який дає Claude
доступ до бази даних, і забирає додому робочий репозиторій, який може
перенести на власні дані.

Після воркшопу учасник уміє:

- пояснити, що таке MCP і чим тул відрізняється від промпту;
- написати MCP-сервер на Python і підключити його до Claude Desktop;
- дати моделі read-only доступ до Postgres без ризику зламати базу;
- розуміти, які тули писати не треба, бо модель уже це вміє;
- віддати ML-модель моделі як інструмент;
- задеплоїти сервер, щоб ним користувалась команда.

**Попередні знання про MCP не потрібні.**

## 2. Принципи дизайну

**Тонкий сервер.** Сервер робить лише те, чого Claude не може сам:
дістатись до бази, зберегти файл, порахувати ML-модель. Усе інше —
аналіз, SQL, графіки, висновки — робить модель.

**Не дублювати модель.** Claude уже малює графіки й будує HTML-звіти
краще, ніж це зробить наш тул із трьома параметрами. Тул `build_chart`
звужує широкий інтерфейс до вузького. Це окремий меседж воркшопу.

**Безпека в базі, не в коді.** SQL-guard у Python — зручність.
Гарантія — роль у Postgres з `GRANT SELECT`. Guard обходиться,
відсутність права `DELETE` — ні.

**Детермінований сетап.** Однакові дані у всіх → однакові відповіді
Claude → передбачуване демо й відтворюваність вдома.

**Кожна хвилина — або код, або кадр.** Жодних слайдів довше за хвилину.

## 3. Архітектура

```
Claude Desktop
      │  MCP: stdio локально → streamable HTTP при деплої
      ▼
 ai-analyst MCP server (Python, FastMCP)
      ├── schema tools   list_tables, describe_table
      ├── sql tool       run_sql  → guard + audit_log
      ├── report tool    save_report(html)
      └── ml tool        predict_churn → model.pkl
      ▼
 PostgreSQL 16 (Docker) — синтетична edtech-база
```

Код сервера однаковий локально й у хмарі. Змінюється транспорт і
джерело секретів — більше нічого. Це демонструється в кінці.

## 4. База даних

### 4.1 Домен

Синтетичний онлайн-репетиторський сервіс для школярів. Домен обрано
тому, що він інтуїтивний для будь-якої аудиторії й дає природну
churn-задачу.

### 4.2 Схема

| Таблиця | Рядків | Призначення |
|---|---|---|
| `students` | 5 000 | учні |
| `tutors` | 250 | репетитори |
| `subscriptions` | 6 400 | підписки (учень може мати кілька послідовних) |
| `lessons` | ~240 000 | уроки за 18 місяців |
| `payments` | ~38 000 | списання по підписках |
| `support_tickets` | ~4 500 | звернення в підтримку |
| `audit_log` | росте | лог запитів агента |

**tutors**
`tutor_id` PK · `hired_at` · `country` · `status` (active/paused/left) ·

**subscriptions**
`subscription_id` PK · `student_id` FK · `plan`
(monthly/quarterly/annual) · `lessons_per_week` (1–3) · `started_at` ·
`ended_at` (NULL = активна) · `status` (active/cancelled/expired) ·
`mrr_usd` · `cancel_reason`

**lessons**
`lesson_id` PK · `student_id` FK · `tutor_id` FK · `subscription_id` FK ·
`scheduled_at` · `status` (completed/cancelled_by_parent/

не оцінили) · `homework_done` bool

**payments**
`payment_id` PK · `subscription_id` FK · `student_id` FK · `paid_at` ·
`amount_usd` · `status` (succeeded/failed/refunded) · `method`

**support_tickets**
`ticket_id` PK · `student_id` FK · `created_at` · `category` ·
`resolved_at` · `csat` (1–5, nullable)

**audit_log**
`id` PK · `ts` · `tool` · `query` · `rows_returned` · `duration_ms` ·
`status` · `error`

### 4.3 Навмисні пастки

Кожна пастка — привід показати, навіщо взагалі `describe_table` і
коментарі до колонок. Наївний запит дає правдоподібну, але неправильну
цифру.

1. `is_test_account` — внутрішні QA-акаунти, які треба виключати
   скрізь. Найчастіша реальна пастка.
2. `lessons.status` має чотири значення. `COUNT(*)` рахує й скасовані.
3. `payments.status = 'refunded'` — наївний `SUM(amount_usd)` завищує
   виручку.
4. `subscriptions.ended_at IS NULL` означає активну, а не «дані
   відсутні».
5. Учень може мати кілька підписок поспіль — `COUNT(subscription_id)`
   ≠ кількість учнів.

Коментарі до колонок (`COMMENT ON COLUMN`) описують ці пастки, і
`describe_table` їх віддає. Учасник бачить, як опис даних прямо
покращує відповідь моделі.

### 4.4 Генерація

`db/seed.py` з фіксованим `random.seed(42)` — у всіх побайтово однакова
база. Дані в git **не комітяться**, комітиться генератор.

Часовий діапазон рахується відносно `--as-of` (дефолт — сьогодні), тому
дані завжди свіжі, коли б воркшоп не повторювали.

Прапорці: `--dsn` (куди заливати, дефолт — локальний Docker),
`--as-of`, `--students`.

Швидкість: завантаження через `COPY`, ціль — під 20 секунд на
ноутбуці. Сідинг запускається автоматично при першому
`docker compose up`.

Правдоподібність: сезонність (провал улітку й на свята), розподіл
активності з довгим хвостом, кореляція рейтингу репетитора з
утриманням учня, зростання скасувань і no-show за 3–4 тижні до відтоку.
Останнє критичне — без нього churn-модель не матиме чого вчити.

### 4.5 Ролі

`db/roles.sql` створює `analyst_ro`: `GRANT CONNECT`, `GRANT USAGE ON
SCHEMA public`, `GRANT SELECT ON ALL TABLES`, плюс `INSERT` лише на
`audit_log`. Сервер ходить у базу тільки під цією роллю.

На воркшопі це показується наживо: просимо Claude видалити таблицю, він
чесно намагається, база відмовляє. Кадр, який запам'ятовується краще за
будь-який слайд про безпеку.

## 5. MCP-сервер

Python 3.11+, FastMCP, `psycopg[binary,pool]`. Приблизно 200 рядків
змістовного коду.

### 5.1 Інструменти

**`list_tables() -> list[dict]`**
Назва, кількість рядків, опис таблиці з `COMMENT ON TABLE`. Перший тул,
який учасник бачить у роботі.

**`describe_table(table: str) -> dict`**
Колонки, типи, nullable, коментарі, зовнішні ключі, 3 приклади рядків.
Саме тут пастки з 4.3 доїжджають до моделі.

**`run_sql(query: str, limit: int = 1000) -> dict`**
Повертає `columns`, `rows`, `row_count`, `truncated`, `duration_ms`.

Guard: єдина інструкція; дозволені лише `SELECT` і `WITH`; заборонені
крапка з комою всередині, коментарі `--`/`/* */`, DDL/DML-ключові
слова; примусовий `LIMIT`; `statement_timeout = 15s`.

Кожен виклик пише рядок в `audit_log` — і успішний, і помилковий.

**`save_report(html: str, name: str) -> dict`**
Кладе готовий HTML у `./reports/<дата>-<name>.html`, повертає
абсолютний шлях. Валідує ім'я файлу (без `..` і слешів). Claude малює,
сервер зберігає.

**`predict_churn(student_ids: list[int] | None = None) -> dict`**
Скорить учнів локальною моделлю. Без аргументу — всіх активних.
Повертає `student_id`, `churn_probability`, `top_factors`, `as_of`.

### 5.2 Чого свідомо немає

`build_chart` — Claude малює краще.
`explain_metric` / контекстний шар — надлишково для 50 хвилин;
коментарі до колонок закривають ту саму потребу.
Кеш, ретраї, пагінація — шум, який ховає суть.

Список «чого немає і чому» проговорюється вголос. Це вчить тому, чого
не вчать туторіали: MCP-сервер має бути малим.

## 6. Churn-модель

`ml/train.py` — окремий скрипт, запускається один раз при сетапі,
навчається за секунди, кладе `ml/model.pkl`.

**Ціль:** учень із активною підпискою на дату зрізу перестає займатись
протягом наступних 30 днів (підписка скасована або жодного
завершеного уроку).

**Ознаки** (усі рахуються одним SQL із наявних таблиць):
завершених уроків за 28 днів · частка no-show за 28 днів · середній
рейтинг за 28 днів · днів з останнього уроку · змін репетитора за 90
днів · невдалих платежів за 90 днів · звернень у підтримку за 90 днів ·
вік підписки в днях · план · план-факт по уроках на тиждень.

**Модель:** `GradientBoostingClassifier` зі sklearn. Трейн/тест по
часу, не випадково — зріз до дати X вчить, після X перевіряє. Очікуваний
ROC AUC 0.75–0.85; якщо вийде 0.99, генератор занадто прямолінійний і
його треба зашумити.

`top_factors` — внесок ознак через SHAP, якщо встановиться швидко,
інакше `feature_importances_` плюс значення ознак конкретного учня.

Модель у git не комітиться, тренується під час `make setup`.

### Гілки

`workshop-start` — робочий каркас із `# TODO (пишемо разом)` рівно в
тих місцях, які набираються в кадрі. Сідинг, docker-compose, генератор

## 8. Сценарій 50 хвилин

| Хв | Блок | Що в кадрі | Що забирає учасник |
|---|---|---|---|
| 0–8 | MCP за 8 хвилин | Сервер з одним тулом `ping` → конфіг Claude Desktop → Claude бачить тул | MCP — це процес із тулами, не магія |
| 8–20 | База | `list_tables`, `describe_table`, `run_sql` → перше справжнє питання до даних | Claude сам пише SQL, якщо бачить схему |
| 20–28 | Безпека | `analyst_ro`, guard, ліміт, `audit_log`. Просимо Claude видалити таблицю — база відмовляє | Безпека живе в базі, не в промпті |
| 28–38 | Візуалізація | Просимо графік → Claude малює сам → додаємо `save_report` → відкриваємо HTML | Не пиши тули на те, що модель уже вміє |
| 38–45 | ML | `predict_churn`, Claude комбінує скоринг із SQL в одній відповіді | Тул — міст до всього, чого LLM не може |
| 45–50 | Деплой | Той самий код по HTTP на Railway, підключення за 30 секунд, `NEXT-STEPS.md` | Деплой не переписує агента |

**Кульмінація** — 20–28 хвилина. Відмова бази у відповідь на `DROP` —
найсильніший кадр воркшопу, бо знімає головне заперечення аудиторії
(«я не пущу AI у продакшн-базу»).

### Питання, які ставимо Claude наживо

Готуються заздалегідь, перевіряються напередодні, лежать у
`docs/DEMO-SCRIPT.md`:

1. «Що взагалі є в цій базі?» — після 8-ї хвилини
2. «Скільки уроків провели минулого місяця і як це відносно
   попереднього?» — після 20-ї, з пасткою `status`
3. «Побудуй графік виручки по місяцях у розрізі каналу залучення» —
   28-а
4. «Хто з активних учнів у зоні ризику і що з ними спільного?» — 38-а

Питання 2 і 4 навмисно містять пастки — модель або сама зазирне в
коментарі колонок, або помилиться, і це стане уроком.

## 9. Помилки — і в сервері, і в кадрі

Кожен тул повертає осмислену текстову помилку, а не трейсбек. Модель
читає помилку й виправляється сама — і це показується наживо: даємо
свідомо криву назву таблиці, Claude отримує «table not found, доступні:
…» і перепитує правильно.

Це вчить головного про дизайн тулів: **повідомлення про помилку — це
теж інтерфейс для моделі.**

## 10. Тестування

Мінімум, який реально боронить демо:

- `test_sql_guard.py` — набір запитів, які guard мусить відбити
  (`DROP`, `DELETE`, дві інструкції, коментар, `; --`), і набір, які
  мусить пропустити;
- `test_seed.py` — після сідингу перевіряються інваріанти: немає
  сиріт по FK, є активні підписки, частка no-show у розумних межах,
  churn-мітка не вироджена;
- `test_tools_smoke.py` — кожен тул викликається на живій базі й
  повертає очікувану форму;
- прогін усього сценарію напередодні воркшопу зі свіжого клону.

## 11. Деплой

`deploy/Dockerfile` пакує сервер; транспорт перемикається змінною
`MCP_TRANSPORT=stdio|http`. На воркшопі підключаємось до заздалегідь
задеплоєного інстансу — живий деплой у останні п'ять хвилин надто
ризикований.

`deploy/AUTH.md` описує, що для команди правильний шлях — вхід через
корпоративний акаунт, а не роздані токени: видимо, хто що дивився, і
відкликання доступу — це вимкнення людини в SSO, а не полювання за
ключами. Чесно кажемо, що це найдовша в реалізації частина, і що вона
свідомо винесена за межі 50 хвилин.

## 12. Хендаут `NEXT-STEPS.md`

1. Перевести на свою базу — що поміняти (`db.py`, `.env`, коментарі до
   колонок) і чого не чіпати.
2. Створити read-only роль у себе — готовий SQL.
3. Описати колонки коментарями. Найдешевше, що радикально покращує
   відповіді. Шаблон і антипатерни.
4. Увімкнути `audit_log` і навіщо він при розборі інцидентів.
5. Задеплоїти для команди — покроково, з розділом про авторизацію.
6. Куди рости: свої тули під ваші системи, публікація звітів, задачі в
   трекері, підключення документації з приватних репозиторіїв.
7. Чого не робити: тули-обгортки над тим, що модель уже вміє; запис у
   базу без людського підтвердження; «дати AI повний доступ, а там
   розберемось».

## 13. Ризики

| Ризик | Пом'якшення |
|---|---|
| Docker не встановлений / повільно тягнеться | Pre-work за 2 дні + чеклист самоперевірки; план Б — DSN до спільної read-only бази на хостингу |
| Claude Desktop не бачить сервер | `TROUBLESHOOTING.md` + слайд із трьома найчастішими причинами; асистент у чаті |

| Не влізаємо в тайминг | Блок ML стискається до показу без набору коду; деплой — до двох хвилин |
| Різні ОС у залі | Перевірити macOS і Windows/WSL напередодні; шляхи в конфізі — абсолютні, з прикладами для обох |

## 14. Відкриті питання

- **Postgres чи MySQL.** Спека написана під Postgres. Якщо цільовий
  інстанс — MySQL, змінюється `server/db.py`, драйвер, `schema.sql`
  (`text[]` → окрема таблиця, `COMMENT ON` → інший синтаксис) і
  `docker-compose.yml`. Решта не міняється.
- **Розмір бази.** 5 000 учнів / 240 000 уроків обрано як баланс між
  швидкістю сідингу й правдоподібністю. Зменшується параметром, якщо
  на слабких ноутбуках буде повільно.
