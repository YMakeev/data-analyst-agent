# Деплой з базою на Neon

Розділення обов'язків: **Neon** тримає базу, **Railway** крутить MCP-сервер.
Код сервера не змінюється — змінюються лише змінні оточення.

Локальний Docker при цьому нікуди не дівається: на воркшопі всі працюють
з ним, а Neon — це та база, до якої підключається задеплоєний інстанс.

---

## Крок 1. Проєкт у Neon

Створи проєкт, у ньому базу `analytics`. Neon видасть рядок підключення
власника — він виглядає приблизно так:

```
postgresql://neondb_owner:ПАРОЛЬ@ep-xxx.eu-central-1.aws.neon.tech/analytics?sslmode=require
```

Це **адмінський** рядок. Серверу він не дістанеться.

### Який ендпоінт брати

Neon дає два хости: звичайний і з `-pooler` у назві. **Бери звичайний**,
без `-pooler`: пул з'єднань у нас свій (`server/db.py`), і другий пул згори
нічого не додає.

Якщо все ж візьмеш pooler-ендпоінт — теж працюватиме: автоматичні prepared
statements у пулі вимкнені саме через те, що вони ламаються об pgbouncer
у transaction mode. Але без потреби ускладнювати не варто.

---

## Крок 2. Схема і read-only роль

Neon не виконує `db/init/*.sql` сам — це вміє тільки локальний контейнер.
Розгортаємо явно:

```bash
python db/bootstrap.py --dsn "postgresql://neondb_owner:...@ep-xxx.../analytics?sslmode=require"
```

Скрипт створить сім таблиць з усіма коментарями, роль `analyst_ro` і надрукує
готовий рядок підключення для сервера.

**Це найважливіший крок усього деплою.** Neon видає рядок із правами на все;
якщо покласти його в `DATABASE_URL`, вся історія з read-only роллю
перетвориться на декорацію, а `prove_readonly.py` почне показувати
«ДОЗВОЛЕНО» замість «ВІДМОВЛЕНО».

Задай свій пароль замість дефолтного:

```bash
ANALYST_RO_PASSWORD='щось-своє' python db/bootstrap.py --dsn "..."
```

## Крок 3. Дані

```bash
python db/seed.py --dsn "postgresql://neondb_owner:...@ep-xxx.../analytics?sslmode=require"
```

Локально це займає п'ять секунд, через інтернет — кілька хвилин: 171 000
рядків їдуть по мережі. Якщо чекати не хочеться, зменш обсяг:

```bash
python db/seed.py --dsn "..." --students 1500
```

Пастки в даних лишаються робочими й на меншому обсязі — перевіряється
тестами `test_lesson_count_trap_is_material` і `test_revenue_trap_is_material`.

Перевір, що вийшло:

```bash
DATABASE_URL="postgresql://analyst_ro:ПАРОЛЬ@ep-xxx.../analytics?sslmode=require" \
    python scripts/prove_readonly.py
```

Має бути п'ять «ВІДМОВЛЕНО» і одне «ДОЗВОЛЕНО».

## Крок 4. Сервер на Railway

У змінних оточення сервісу:

```
DATABASE_URL   = postgresql://analyst_ro:ПАРОЛЬ@ep-xxx.../analytics?sslmode=require
MCP_TRANSPORT  = http
```

`SEED_ON_START` **не став** — дані вже залиті кроком 3, а зайвий рестарт із
цим прапорцем перезапише базу.

`ADMIN_DATABASE_URL` серверу теж не потрібен: він знадобиться лише при
першому тренуванні моделі. Якщо хочеш, щоб контейнер натренував її сам —
додай адмінський рядок тимчасово, дочекайся старту й прибери. Або натренуй
локально і поклади `ml/model.pkl` в образ.

Далі Settings → Networking → Generate Domain. Посилання для команди:

```
https://<домен>.up.railway.app/mcp
```

## Що Neon робить інакше, ніж звичайний Postgres

**Присипляє базу.** На безкоштовному тарифі compute вимикається після
5 хвилин простою. Перший запит після паузи будить його — це близько секунди,
не страшно. Але пул мусить розуміти, що старі з'єднання померли: у
`server/db.py` для цього стоять `check=ConnectionPool.check_connection`
і `max_idle=120`. Без них перший запит після паузи впав би з
`connection already closed` — рівно посеред воркшопу, поки ти говорила.

**Вимагає SSL.** `?sslmode=require` у рядку обов'язковий.

**Обмежує з'єднання.** Наш пул тримає максимум чотири — з великим запасом.

**Уміє гілки.** Neon робить копію бази за секунди, без копіювання даних.
Це найкращий план Б для воркшопу: якщо в когось не встав Docker, даєш йому
гілку бази й рядок підключення — і людина працює нарівні з усіма, нічого не
встановлюючи. Варто підготувати заздалегідь.
