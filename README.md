# AI-аналітик: MCP-сервер над базою даних

Ти підключаєш Claude до бази даних і питаєш її людською мовою. Claude сам
дивиться, які є таблиці, читає їхню структуру, пише SQL, будує графіки й
звертається до ML-моделі.

Робить це не магія, а маленький Python-сервер зі **150 рядків змістовного
коду** — той, що в цьому репозиторії. Він називається MCP-сервером, і
наприкінці ти зможеш написати такий самий для своїх даних.

Попередні знання про MCP не потрібні.

```
Ти  →  Claude  →  MCP-сервер  →  база даних
```

---

## Що вміє цей агент

П'ять інструментів. Claude сам вирішує, що і в якому порядку викликати.

| Інструмент | Що робить |
|---|---|
| `list_tables` | які є таблиці, скільки в них рядків, про що вони |
| `describe_table` | колонки, типи, зв'язки та пояснення особливостей даних |
| `run_sql` | виконує SELECT-запит: тільки читання, з лімітом і таймаутом |
| `save_report` | зберігає HTML-звіт, який Claude намалював сам |
| `predict_churn` | оцінює ризик відтоку учня ML-моделлю |

Інструмента «побудувати графік» тут немає **навмисно**. Claude малює
візуалізації краще, ніж це зробив би тул із трьома параметрами. Наша справа —
зберегти готовий результат у файл, щоб його можна було переслати колезі.

## Крок 1. Що встановити

Докладно, з перевірками на кожному кроці — [docs/SETUP.md](docs/SETUP.md).
Якщо коротко, потрібні три речі:

- **Python 3.10 або новіший** — [python.org](https://www.python.org/downloads/)
- **Claude Desktop** — [claude.ai/download](https://claude.ai/download)
- **Git** — щоб завантажити цей репозиторій

Docker потрібен лише в одному з двох варіантів роботи з базою — про це нижче.

## Крок 2. Завантажити проєкт

```bash
git clone https://github.com/hpylieva/data-analyst-agent.git
cd data-analyst-agent
python3 -m venv .venv
source .venv/bin/activate
```

На Windows остання команда інша: `.venv\Scripts\activate`

```bash
pip install -e ".[dev]"
cp .env.example .env
```

## Крок 3. Підключити базу даних

Два варіанти. Обери один.

### Варіант А — база, яку дає ведуча (нічого не встановлюєш)

Отримуєш готовий рядок підключення й вставляєш його у файл `.env` у рядок
`DATABASE_URL`:

```
DATABASE_URL=postgresql://analyst_ro:ПАРОЛЬ@хост.neon.tech/workshop_analytics?sslmode=require
```

Все. Дані вже там, нічого запускати не треба.

### Варіант Б — своя база на твоєму комп'ютері

Потрібен [Docker Desktop](https://www.docker.com/products/docker-desktop/) —
постав і **запусти застосунок**, він має працювати у фоні.

```bash
make setup
```

Ця команда підніме Postgres у контейнері, згенерує дані й натренує
ML-модель. Дві-три хвилини. Нічого редагувати не треба: `.env` уже налаштований
саме на цю базу.

Варіант Б цікавіший тим, що база лишається в тебе назавжди — можна ламати,
експериментувати й повертати одною командою `make reset`.

## Крок 4. Підключити сервер до Claude

```bash
make config
```

Команда надрукує готовий шматок конфігурації **з правильними шляхами саме для
твого комп'ютера** і скаже, у який файл його вставити. Не пиши шляхи руками —
це найчастіша причина, чому нічого не працює.

Після цього **повністю вийди з Claude Desktop** і запусти знову:

- macOS — `Cmd+Q`, не просто закрити вікно
- Windows — вийти через іконку в треї

Конфігурація читається лише при старті застосунку.

## Крок 5. Перевірити

Відкрий новий чат у Claude і спитай:

> Що є в цій базі?

Claude має перелічити сім таблиць і коротко описати, що це за сервіс. Якщо
так — готово, агент працює.

Не вийшло — [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md), там розібрані
причини в порядку від найчастішої.

## Що спитати далі

Питання, на яких добре видно, як агент працює:

> Скільки уроків ми провели минулого місяця?

> Побудуй графік проведених уроків по місяцях за останній рік

> Збережи цей звіт файлом

> Хто з учнів у зоні ризику і що в них спільного?

Розгорни виклики інструментів у відповіді Claude — там видно ланцюжок:
спершу він подивився список таблиць, потім прочитав структуру потрібної,
потім написав SQL. Цей порядок ніхто не програмував, модель обрала його сама.

## Як це влаштовано

```
Claude Desktop
      │   MCP: локально через stdio, у хмарі через HTTP
      ▼
 MCP-сервер (Python)
      ├── server/main.py        реєстрація інструментів, вибір транспорту
      ├── server/db.py          підключення, захист SQL, зрозумілі помилки
      ├── server/tools/         власне інструменти
      └── server/features.py    ознаки ML-моделі
      ▼
 PostgreSQL
```

Три речі, на які варто звернути увагу в коді:

**Опис інструмента для моделі — це його docstring.** Не назва функції й не
назва файлу. Claude читає текст під `def` і з нього розуміє, що робить
інструмент і коли його викликати. Зміниш docstring — зміниться поведінка.

**Знання про дані живуть у самій базі.** Пояснення на кшталт «ось цей статус
означає скасований урок, не рахуй його» записані як коментарі до колонок
(`COMMENT ON COLUMN`), а `describe_table` віддає їх моделі. Не в промпті, не в
коді — поруч із даними.

**Різниця між локальним запуском і сервісом для команди — одна змінна.**
Локально Claude Desktop сам запускає сервер як дочірній процес і говорить із
ним через stdin/stdout. У хмарі сервер слухає HTTP-порт. Код інструментів
однаковий, перемикає це `MCP_TRANSPORT`.

## Безпека

Сервер ходить у базу під користувачем, який має право **лише читати**. Це не
перевірка в коді, а права на рівні Postgres: навіть якщо запит якось пролізе
повз усі перевірки, база його відхилить.

Переконатись самому:

```bash
python scripts/prove_readonly.py
```

Скрипт іде в базу напряму, повз увесь код сервера, і намагається видалити
таблицю, стерти дані й підчистити журнал. Усе отримує відмову; читання
проходить.

Кожен виклик пишеться в таблицю `audit_log` — і успішний, і невдалий. Агент
має право туди тільки додавати: журнал, який можна підчистити, журналом не є.

## Команди

```bash
make setup    # підняти базу, поставити залежності, згенерувати дані, натренувати модель
make config   # показати конфігурацію для Claude Desktop
make run      # запустити сервер вручну, щоб побачити помилки
make test     # прогнати тести
make reset    # знести базу й зібрати заново
```

## Дві гілки

`main` — повне рішення.

`workshop-start` — каркас, який ми заповнюємо разом на воркшопі: там навмисно
не написані ті функції, які набираємо в кадрі. Якщо відстанеш —
`git checkout main` повертає робочий стан. Деталі:
[docs/WORKSHOP-START.md](docs/WORKSHOP-START.md).
